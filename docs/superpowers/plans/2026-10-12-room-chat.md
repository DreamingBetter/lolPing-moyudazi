# Room Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a dedicated plain-text group chat page for rooms, with in-memory history handoff of the latest 50 messages and lightweight local send-failure states.

**Architecture:** Keep all room chat networking, validation, encryption, history merging and rate limiting inside the main process `RoomManager`. Add narrow settings IPC methods and a pushed `RoomChatState`; the renderer only renders the Chat section, submits text, and requests retries. Reuse the existing LAN/relay transports and the existing settings-window section navigation.

**Tech Stack:** Electron 44, Node/TypeScript, React 19, Fluent UI, Vitest, existing AES-256-GCM room envelope, existing LAN and Nostr relay transports.

## Global Constraints

- Keep `PROTOCOL_VERSION` at `1`; older clients drop unknown chat message types and continue exchanging existing ping/emote messages.
- Keep chat history in memory only, limited to the latest **50 messages** with no time-based expiry; clear it when the local client leaves or quits the room.
- Keep chat text plain text, trimmed and non-empty, at most 1000 Unicode code points, and reject text whose encoded room packet cannot fit the existing 1200-byte sealed-packet limit.
- Split history responses into packet-sized `chatHistory` parts; each part has `part < total`, with `total <= 256`.
- Chat must not be blocked by room mute, global pause, per-member mute or ping/emote rate settings.
- Use a separate chat outgoing limiter of 3 messages/second with burst 6 and incoming per-peer limiter of 5 messages/second with burst 10.
- Do not add disk persistence, server persistence, private messages, files, images, stickers, reactions, edits, deletion, read receipts, delivery counts, search or threads.
- Do not add dependencies.
- Preserve unrelated existing worktree changes in `AGENTS.md`, `native/hook-helper/build.cmd`, `native/hook-helper/tests/helper_tests.cpp`, and `.idea/`.

- [ ] **Step 5: Implement local chat send and retry**

Add:

```ts
sendChat(text: string): ChatSendResult
retryChat(id: string): ChatSendResult
```

Implementation order for `sendChat`:

1. Require `phase === 'active'` and `keys !== null`; otherwise return `not-in-room`.
2. Call `sanitizeChatText`; return `empty` for empty output and `too-long` for a code-point or sealed-packet budget violation.
3. Apply `chatOutgoing.allow(this.self, CHAT_OUTGOING_RATE, CHAT_OUTGOING_BURST)`; return `failed` when the bucket is exhausted.
4. Generate a 32-character lowercase hex ID from `deps.randomBytes(16)`.
5. Append `{ id, peer: self, name, color, ts, text, self: true, status: 'sending' }` and emit chat state.
6. Seal/send the `chat` body through `sendShared({ respectPause: false, useRelayCap: false })`.
7. Set the record to `sent` on success or `failed` on failure, emit chat state, and return the corresponding result.

`retryChat` must find a local record with the requested ID and `status === 'failed'`, revalidate the current room state, set it to `sending`, reuse its existing ID/text, send once, then set `sent` or `failed`. It must never create a second record.

Packet-size validation must be authoritative in main. Build a worst-case candidate with a maximum-length peer, request ID, sequence, timestamp and 16-code-point name, then use the existing `seal()` limit before accepting local text. This guarantees that the same text can fit as both a standalone chat message and a one-item history message; tests must cover quotes, CJK and emoji because UTF-8 and JSON escaping change byte size.

- [ ] **Step 6: Implement incoming chat and history merge**

In `onPacket`, handle `chatHistoryRequest`, `chatHistory` and `chat` after replay validation, member lookup and `heard()`, but before ping/emote pause/mute/update gates:

- `chat`: require a known member, apply `chatIncoming` by sender peer, dedupe by `msg.id`, append `{ ...msg, name: member.name, color: member.color, self: false }`, sort and trim to 50, then emit.
- `chatHistoryRequest`: require a known member and send the current cache of `sent`/remote messages, excluding local `sending`/`failed` records.
- `chatHistory`: require a known member, match a pending request, dedupe by `senderPeer:part`, merge validated items by message ID, mark matching local IDs `sent`, sort and trim to 50, then emit.

History response algorithm:

1. Convert the current cache to `ChatHistoryItem[]` and take the last 50 chronological records.
2. Build candidate `chatHistory` bodies using `part: 255` and `total: 256` while packing items.
3. Before appending an item, attempt to seal the candidate with the current room key. If it would exceed 1200 bytes, close the current part and start the next one.
4. Set the actual `total` after packing and seal/send each part with its own room sequence number.
5. Send all parts through `sendShared({ respectPause: false, useRelayCap: false })`.

The first valid presence observed in a join session triggers one `chatHistoryRequest`. Keep its request ID in `pendingHistory`; expire it after 30 seconds. A later member joining does not cause an already-active client to repeatedly request history, while every new joiner still requests once for itself.

export function useChatState(): RoomChatState | null {
  const [chat, setChat] = useState<RoomChatState | null>(null);
  useEffect(() => {
    let pushed = false;
